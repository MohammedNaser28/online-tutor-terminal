# CHALLENGE_IPC.md — File-Based IPC Security Analysis

## 1. File Paths and Location

All IPC files live at a single well-known path relative to the session rootfs:

```
# Host-side absolute path:
{sessionRootfs}/rootfs/tmp/.qo-challenge-req
{sessionRootfs}/rootfs/tmp/.qo-challenge-resp
{sessionRootfs}/rootfs/tmp/.qo-challenge-debug

# Where sessionRootfs = /tmp/qo-sessions/{studentID}-{4-char-hex}
# e.g. /tmp/qo-sessions/student42-a3f1/rootfs/tmp/.qo-challenge-req
```

**Inside the sandbox** (after pivot_root to `{sessionRootfs}/rootfs`):

```
/tmp/.qo-challenge-req
/tmp/.qo-challenge-resp
/tmp/.qo-challenge-debug
```

### Who can write to these paths?

The sandbox **has no user namespace** (`CLONE_NEWUSER` is not set — `setup_userns()` in `deploy/qo-init.c:39-60` is defined but never called). The student process inside the sandbox runs as host UID 0.

The files are created with mode `0644` by both the server (`server/challenge.go:526`) and the bashrc alias's shell redirections (which inherit the shell's umask, typically `0022`).

**Both `.qo-challenge-req` and `.qo-challenge-resp` are directly writable by the student from inside the sandbox.**

## 2. The `go` (Submit) Flow — Step by Step

### 2a. Bash alias (inside sandbox shell)

When the student types `go` at the shell prompt, the bashrc alias generated by `deploy/qo-init.c:216-252` fires:

```bash
__qo_challenge() {
    local action="$1"
    if [ "$action" = "go" ]; then
        local ans
        read -p "Your answer: " ans          # prompts for answer on PTY
        action="go:${ans}"                    # prepends "go:" prefix
    fi
    local req="/tmp/.qo-challenge-req"
    local resp="/tmp/.qo-challenge-resp"
    local tmpReq="/tmp/.qo-challenge-req.tmp"
    printf '%s' "$action" > "$tmpReq"         # write to temp file first
    mv -f "$tmpReq" "$req"                    # atomic rename to trigger server
    # ... then polls resp file for up to 5 seconds (50 × 0.1s)
}
```

**Written to `.qo-challenge-req`**: the literal string, e.g.:
```
go:my answer here
```
or for other commands:
```
quest
hint
map
status
logo
help
```

The `go` alias **can be trivially bypassed**. The student can write any content directly:
```bash
echo "go:bypass_answer" > /tmp/.qo-challenge-req
echo "quest" > /tmp/.qo-challenge-req
```

### 2b. Server reads the request (`server/challenge.go:406-428`)

The server's `pollChallengeRequests` goroutine polls `.qo-challenge-req` in a tight loop (50ms sleep between iterations):

```go
data, err := os.ReadFile(reqFile)          // line 406
// ...
action := strings.TrimSpace(string(data))
_ = os.WriteFile(reqFile, []byte{}, 0644)   // line 421 — clears req file

goAnswer := ""
if strings.HasPrefix(action, "go:") {       // line 425
    goAnswer = action[3:]                   // everything after "go:"
    action = "go"
}
```

The server extracts `goAnswer` from the IPC file. This is the **only student-supplied input** that reaches the evaluation logic.

### 2c. Server evaluates (`server/challenge.go:461-489`)

```go
case "go":
    level := session.Challenge.Current()
    var passed bool
    var err error

    // Try pure Go validator first
    passed, err = runValidator(session.RootfsPath, level, goAnswer)   // line 468
    if err != nil && level.CheckScript != "" {
        // Fall back to check.sh script
        passed, err = RunCheckScript(session.RootfsPath, ...,
            goAnswer, level.CheckScript)                               // line 471
    }
```

**Pass/fail is determined entirely by the server.** The content of `goAnswer` is used as input to the evaluation, not as the pass/fail result itself. The server never reads `.qo-challenge-resp` — it only writes to it.

### 2d. Server writes response (`server/challenge.go:525-527`)

```go
if resp != nil {
    _ = os.WriteFile(respFile, append(resp, '\n'), 0644)
}
```

The response is purely cosmetic — ANSI-colored text for the student to read in their terminal.

### 2e. Student's shell polls for response

The bashrc alias polls `.qo-challenge-resp` in a 5-second loop, reads and prints the content, then truncates the file. The student sees "✅ Correct!" or "❌ Not quite right."

## 3. Validator Analysis — Trust Boundaries

### `ValidatorFlag` — `answer == v.Value`

```go
case ValidatorFlag:
    return answer == v.Value, nil
```

- `answer` = `goAnswer` = student-supplied string from IPC file.
- `v.Value` = the expected flag, stored in `ChallengeMetadata.Levels[i].Validator.Value`, loaded from the **encrypted archive** via `qo meta` at session start.
- **Verdict**: Server is the authority. No forgery vector. Student either knows the flag or doesn't.

### `ValidatorProcessDead` / `ValidatorProcessRunning`

```go
case ValidatorProcessDead:
    return !processExists(rootfsPath, v.Name), nil
```

`processExists` reads the sandbox's `/proc` from the **host side**:

```go
procDir := filepath.Join(rootfsPath, "rootfs", "proc")
// reads proc/{pid}/cmdline for each numeric entry
return strings.Contains(string(cmdline), v.Name)
```

After pivot_root, `{rootfsPath}/rootfs/proc` IS the sandbox's `/proc` (mounted as procfs by `qo-init.c:302-306`). The student can influence this by starting or killing processes inside the sandbox.

- **Verdict**: Server reads real procfs state. Student CAN create/kill processes to influence the result — but this is **by design** (the challenge task is process management). No forgery of the check result itself — the server independently reads `/proc/*/cmdline`.
- **Escalation risk**: procfs is writable in some configurations; the student could potentially manipulate proc entries. The standard `hidepid=` mount option is NOT used (proc mounted as `MS_NOSUID | MS_NOEXEC | MS_NODEV` only).

### `ValidatorFileExists`

```go
case ValidatorFileExists:
    _, err := os.Stat(filepath.Join(levelDir, v.Path))
    return err == nil, nil
```

- `levelDir` = `{rootfsPath}/rootfs/tmp/levelN/` — determined by the server.
- `v.Path` = from the ChallengeMetadata (encrypted archive, immutable).
- Server reads the actual filesystem at a path IT controls.
- **Verdict**: Trustworthy. The student must actually create the file at the expected path to pass. No forgery of the `Stat` result is possible.

### `ValidatorFileNotExists`

Same mechanism — server stats the path directly. **Verdict**: Trustworthy.

### `ValidatorFileContains`

```go
case ValidatorFileContains:
    data, err := os.ReadFile(filepath.Join(levelDir, v.Path))
    return strings.Contains(string(data), v.Value), nil
```

- `v.Path` and `v.Value` from encrypted archive (immutable).
- Server reads the file content from the sandbox filesystem at a path IT controls.
- **Verdict**: Trustworthy. Student must write the required content to the file. The actual file content is read by the server — no assertion from the student is trusted.

### `ValidatorFilePerms`

```go
case ValidatorFilePerms:
    info, err := os.Stat(filepath.Join(levelDir, v.Path))
    mode := fmt.Sprintf("%o", info.Mode().Perm())
    return mode == v.Mode, nil
```

- `v.Path` and `v.Mode` from encrypted archive (immutable).
- Server stats the file directly. **Verdict**: Trustworthy.

### Summary of validator trust

| Validator | Server reads from | Student-influenced? | Forgeable? |
|-----------|-------------------|---------------------|------------|
| `flag` | In-memory `v.Value` (from encrypted archive) | No (answer supplied, compared to stored secret) | No |
| `process_dead` | `{rootfs}/rootfs/proc/{pid}/cmdline` | Yes (by design — student manages processes) | No (server reads procfs independently) |
| `process_running` | `{rootfs}/rootfs/proc/{pid}/cmdline` | Yes (by design) | No |
| `file_exists` | `{rootfs}/rootfs/tmp/levelN/{path}` | Yes (by design — student creates files) | No |
| `file_not_exists` | `{rootfs}/rootfs/tmp/levelN/{path}` | Yes (by design) | No |
| `file_contains` | `{rootfs}/rootfs/tmp/levelN/{path}` | Yes (by design) | No |
| `file_perms` | `{rootfs}/rootfs/tmp/levelN/{path}` | Yes (by design) | No |

**All validators are trustworthy.** The server independently inspects the sandbox filesystem or process state at every evaluation. No student-supplied metadata is used as a pass/fail result.

## 4. Response File Forgery

**Can the student write to `.qo-challenge-resp` directly?** Yes — immediately, with no restriction.

**Does this matter?** No — for the following reasons:

1. The server **never reads** `.qo-challenge-resp`. It only writes to it.
2. The challenge state (`ChallengeState.CurrentLevel`, `Completed`, `score`) lives entirely in server memory, managed by `pollChallengeRequests`.
3. The only reader of `.qo-challenge-resp` is the student's own bashrc alias, which `cat`s the content for display purposes.

A student who writes `"🎉 Correct! You completed all levels!"` to `.qo-challenge-resp` will see that text printed in their terminal, but the server's `ChallengeState` is unchanged — no `Advance()`, no `IncrementScore()`, no progression.

**Direct forgery vector: NONE.** The IPC is one-way for results (server→student).

## 5. meta.yaml / question.txt / hint.txt Tampering

### meta.yaml

**Never extracted into the sandbox.** From `qo/pkg/archive/decrypt.go:161-163`:

```go
if isMetaFile(header.Name) {
    continue // meta.yaml is server-side only — never extracted to sandbox
}
```

The server reads the metadata exclusively via `LoadChallengeMeta` (`server/challenge.go:112-129`), which runs `qo meta` as a subprocess against the **original encrypted archive file** on the host filesystem.

- **Student cannot modify** — the file isn't in the sandbox.
- **Server never reads from sandbox** — always from the encrypted archive.
- **Tampering impact**: None.

### question.txt / hint.txt

These ARE extracted into the sandbox (they're regular files in the archive, not named `meta.yaml`). Final path:

```
{rootfs}/rootfs/tmp/level1/question.txt
```

From the sandbox's perspective:
```
/tmp/level1/question.txt
```

The student can read and modify these files. However:

**The server never re-reads them from the sandbox in normal operation.** Questions and hints are served from `session.Challenge.Levels[i].Question` / `.Hint`, which are populated from the metadata at session start in `ws.go:220-252` (via `LoadChallengeMeta` → `DecryptMetadata` → `normalizeMeta`).

**One exception**: `DiscoverLevelsFromRootfs` (`server/challenge.go:297-338`) reads `question.txt` and `hint.txt` from the sandbox filesystem. This is used ONLY as a fallback when the metadata has no levels defined (the `needsDiscovery` branch at `challenge.go:372-388`). In the normal flow (meta.yaml has levels), this path is never reached.

- **Student CAN modify these files**, but in normal operation this affects nothing because the server serves questions/hints from its in-memory `ChallengeState` (loaded from the encrypted archive).
- **Tampering impact in normal flow**: Cosmetic only — the files inside the sandbox are stale copies.
- **Tampering impact in edge case** (no meta.yaml levels): The student could change the question text or hint. This is a minor tampering vector but doesn't affect scoring (only `quest`/`hint` display text, and only in the metadata-less fallback mode).

### `check.sh` and `init.sh`

These ARE extracted into the sandbox initially, but:

1. At session start, `loadCheckScripts` (`server/challenge.go:153-183`) reads `check.sh` and `init.sh` content from the sandbox into **server memory**.
2. Immediately after reading, it **deletes the files from the sandbox** (`os.Remove(checkPath)` at line 169, `os.Remove(initPath)` at line 177).
3. All subsequent evaluations use the in-memory copy. The server runs `check.sh` by feeding the stored content to `/bin/bash -s` on the **host side** (not inside the sandbox).

The deletion window is race-prone: `loadCheckScripts` waits up to 3 seconds (30 × 100ms) for the level directory to appear. If the student can write to the file before the server reads it... but at session start, the archive has just been extracted by `qo start`, and `loadCheckScripts` runs immediately. The student doesn't have shell access yet (the sandbox process is still starting). By the time the student gets a shell, the files are already deleted.

- **Student cannot modify** after session starts (files are deleted).
- **Run context**: check.sh runs as a host-side subprocess of the server. It accesses the sandbox filesystem for file-based checks (by design). The script itself cannot be tempered with.

## 6. quest/hint/map/status — Data Flow Direction

All four handlers **serve data to the sandbox** — they never accept data from it:

### `quest` (challenge.go:431-449)
- Reads from `session.Challenge.Current()` — in-memory `ChallengeState`.
- Runs `init.sh` if first access to this level (also from in-memory copy).
- Writes result (question text) to `.qo-challenge-resp`.
- **No read from sandbox** (except `init.sh` execution, which writes no output back).

### `hint` (challenge.go:450-459)
- Reads from `session.Challenge.Current().Hint` — in-memory.
- Writes to `.qo-challenge-resp`.
- **No read from sandbox.**

### `map` (challenge.go:490-503)
- Reads from `session.Challenge.Status()` — in-memory state machine.
- Writes to `.qo-challenge-resp`.
- **No read from sandbox.**

### `status` (challenge.go:504-516)
- Reads from `session.Challenge.Current()` — in-memory.
- Writes to `.qo-challenge-resp`.
- **No read from sandbox.**

### `logo` (challenge.go:517-518)
- Returns hardcoded string `"QO Logo"`.
- **No read from sandbox.**

### `help` (challenge.go:519-520)
- Returns hardcoded command listing.
- **No read from sandbox.**

### Summary

| Handler | Reads from sandbox? | Writes to sandbox? | Student-influenced? |
|---------|--------------------|--------------------|--------------------|
| `quest` | init.sh execution on host (harmless) | `.qo-challenge-resp` | No |
| `hint` | No | `.qo-challenge-resp` | No |
| `go` | Filesystem/proc for validation | `.qo-challenge-resp` | Answer string only (input, not result) |
| `map` | No | `.qo-challenge-resp` | No |
| `status` | No | `.qo-challenge-resp` | No |
| `logo` | No | `.qo-challenge-resp` | No |
| `help` | No | `.qo-challenge-resp` | No |

## 7. Overall Security Assessment

### Current design is forgery-resistant.

The critical trust property holds: **the server is the sole authority on pass/fail and challenge state progression.** No path exists where student-supplied content (from `.qo-challenge-req` or from the sandbox filesystem) directly determines a pass/fail result without the server independently verifying it against known-good data.

### Honest gaps worth documenting (not exploit-grade, but design-weakness-grade):

1. **No user namespace** — If a student kernel-exploits their way out of the namespace jail (no seccomp by default, missing `CLONE_NEWUSER`), they could tamper with IPC files on the host filesystem arbitrarily. But at that point the sandbox is already fully compromised and game-over is assumed.

2. **`processExists` procfs visibility** — `/proc` inside the sandbox shows all sandbox-internal processes. A student can see and potentially interact with processes started by other mechanisms. The `process_dead`/`process_running` validators are intended to be influenced by student actions, but there's no isolation between "challenge processes" and "student-started processes" within the sandbox.

3. **`DiscoverLevelsFromRootfs` fallback reads student-writable files** — If meta.yaml has no levels defined, the server falls back to reading `question.txt`/`hint.txt` from the sandbox filesystem. This is a minor cosmetic tampering vector (the student could change what `quest` displays). It does not affect scoring or progression.

4. **`loadCheckScripts` timing dependency** — Uses a 3-second polling window to find and read level directories. If the archive extraction is delayed (slow I/O), the server might miss the window and leave `check.sh`/`init.sh` in the sandbox. The student would then find readable script files, possibly revealing validation logic. This is a **confidentiality leak**, not a forgery vector — the files would still be read-and-deleted on the next `quest` access.

5. **`init.sh` runs as host root** — The init script executes as the server process (host root) inside the sandbox filesystem. A malicious init.sh embedded by the challenge author (not the student) could contain anything. This is an instructor-supply-chain concern, not a student forgery concern.
